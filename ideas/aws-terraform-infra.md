# AWS 배포용 Terraform 인프라

- 상태: 아이디어
- 작성일: 2026-10-12
- 저장소: `BranKein/vive-infra` (비공개, 사용자가 만들 예정, `projects/infra`). 구현 계획은 `projects/infra/PLAN.md`

## 개요

다른 바이브 프로젝트들을 AWS에 띄우기 위한 Terraform 프로젝트다. 그 자체가 서비스라기보다 다른 프로젝트들을 위한 도구 성격의 프로젝트이며, 각 프로젝트의 AWS 인프라를 이 한곳에서 정의하고 관리한다.

## 요구사항

사용자가 말한 내용:

- Terraform 프로젝트를 하나 만든다.
- 다른 바이브 프로젝트들을 AWS에 띄우는 데 필요한 Terraform 코드를 여기서 만들고 관리한다.
- 다른 프로젝트들을 위한 프로젝트(도구)로 쓴다.

## 결정된 사항

사용자가 2026-10-12에 정한 내용:

- **계정**: 사용자의 개인 AWS 계정을 쓴다.
- **접근 방식**: 이 컴퓨터에 설치된 AWS CLI의 자격 증명을 쓴다.
- **apply 실행**: `terraform apply`는 사용자가 직접 실행한다. 에이전트는 실행하지 않는다.
- **호스팅 방식**: 정적 호스팅이 가능한 프로젝트는 S3로 띄운다. 백엔드가 필요한 프로젝트는 가급적 서버리스로 띄운다.
- **예산**: 위 방식이라 월 예산 상한은 당장 신경 쓰지 않는다.
- **도메인**: `yeonhyuk.me`를 쓴다. DNS는 Cloudflare에서 관리하고 있다.
- **Cloudflare**: Cloudflare도 Terraform으로 관리한다. 관리 대상은 프로젝트용 서브도메인 레코드뿐이다. `yeonhyuk.me`에 이미 있는 DNS 레코드는 가져오지 않고 건드리지 않는다.
- **Cloudflare API 토큰**: 사용자가 발급한다. 필요한 시점에 에이전트가 요청하면서 어디에 넣을지 알려주고, 사용자가 직접 넣는다.
- **정적 호스팅 구성**: S3 + CloudFront로 한다. HTTPS는 CloudFront와 ACM 인증서로 처리하고, Cloudflare에는 DNS 레코드만 둔다.
- **주소 체계**: 프로젝트마다 `<프로젝트>.yeonhyuk.me` 형태의 주소를 준다.
- **저장소**: 비공개로 둔다. 공개 루트 저장소가 비공개 저장소를 서브모듈로 참조하는 형태가 된다.

사용자가 2026-10-14에 정한 내용:

- **첫 대상**: warehouse-tycoon을 S3 + CloudFront로 정적 호스팅하고, 배포는 GitHub Actions로 한다.
- **배포 시점**: 태그를 달 때만 배포한다.
- **GitHub Actions의 AWS 인증**: 액세스 키를 쓴다(GitHub Secrets).
- **저장소 이름**: `vive-infra`.
- **진행**: 계획만 먼저 세우고, 구현은 사용량 한도가 초기화된 뒤 사용자가 요청하면 시작한다.

## 미정 사항

사용자가 정해야 하는 것은 현재 없다.

에이전트가 기본값을 제안할 수 있는 것:

- Cloudflare API 토큰의 권한 범위와 전달 방식 (제안: `yeonhyuk.me` 영역의 DNS 편집 권한만 가진 토큰을 환경 변수 `CLOUDFLARE_API_TOKEN`으로 설정)
- 리전 (제안: 서울 `ap-northeast-2`)
- state 저장 위치와 잠금 (제안: S3 백엔드, 프로젝트별로 state 분리)
- 디렉터리 구조 (제안: 공용 모듈 + 프로젝트별 디렉터리)
- 환경 구분 (제안: 처음에는 운영 환경 하나만)
- 서버리스 백엔드의 기본 구성 (제안: Lambda + API Gateway 또는 Function URL, 데이터는 DynamoDB, 예약 실행은 EventBridge Scheduler)
- 비밀 값 관리 (제안: SSM Parameter Store, 저장소에는 값을 넣지 않음)
- 인프라 정의와 애플리케이션 배포의 경계 (제안: 이 저장소는 인프라만, 코드 배포는 각 프로젝트의 CI가 담당)
- Terraform 버전과 provider 버전 고정 방식

## 메모

- 이 프로젝트를 쓰게 될 첫 후보는 [주기적 코딩 문제 생성 및 구독 알림](periodic-coding-problems.md)이다. 예약 실행, 데이터 저장, 메일 발송이 필요해서 서버리스 기본 구성을 정하는 기준 사례가 된다.
- [프로젝트 박물관 사이트](project-museum-site.md)는 정적 호스팅만 있으면 된다.
- 에이전트의 작업 범위: 코드 작성, `terraform fmt`, `validate`, `plan`까지. `apply`와 `destroy`는 사용자가 실행한다. `plan`은 AWS CLI 자격 증명으로 계정을 읽기만 한다.
- AWS 자격 증명과 Cloudflare 토큰은 에이전트가 입력하거나 저장소에 기록하지 않는다.
- 비공개 서브모듈의 영향: 루트 저장소의 `.gitmodules`에 이 저장소의 URL(이름)이 공개된다. 내용은 권한이 없으면 볼 수 없다. 다른 사람이 루트 저장소를 서브모듈까지 포함해 클론하면 이 서브모듈에서만 인증 오류가 난다. 루트 저장소에서 CI를 돌릴 때는 서브모듈을 재귀적으로 가져오지 않도록 하거나 접근 토큰을 줘야 한다.
