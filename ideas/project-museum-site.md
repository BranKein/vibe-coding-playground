# 프로젝트 박물관 사이트

- 상태: 아이디어 (기획 중. 디자인은 Figma로 후보를 받은 뒤 정한다)
- 작성일: 2026-10-12
- 주소: https://vive-museum.yeonhyuk.me (예정)
- 저장소: 미정. 루트 저장소(vive-coding-playground)에 둘지, 박물관 전용 저장소로 뺄지 아래 "미정 사항" 참고

## 개요

정적 사이트 하나에 바이브 코딩 프로젝트들을 박물관처럼 전시한다. 전시품마다 썸네일이 있고, 누르면 그 프로젝트 사이트로 들어간다. 아직 만들지 않은 아이디어는 "준비 중"으로 전시한다. 방문자는 새 아이디어를 남길 수 있다.

## 요구사항

사용자가 말한 내용:

- 정적 사이트일 것
- 다른 프로젝트들을 보여줄 것
- 박물관 같은 느낌일 것
- (2026-10-15) 기능은 간단하게: 프로젝트마다 썸네일이 있고, 누르면 그 프로젝트 사이트로 들어간다.
- (2026-10-15) 다른 프로젝트의 도메인 링크를 알고 있어야 하고, 바뀌면 갱신되어야 한다.
- (2026-10-15) 방문자에게 아이디어를 받는다.
- (2026-10-15) 디자인이 중요하다. 사용자가 Figma MCP를 붙여 디자인 후보를 받아 본 뒤 정한다. 그전에는 구현하지 않는다.

## 결정된 사항

### 주소와 배포 (2026-10-15 사용자 결정)

- 주소는 `vive-museum.yeonhyuk.me`.
- 배포는 다른 프로젝트와 같은 구조를 쓴다([docs/deploy.md](../docs/deploy.md)). vive-infra에 `sites/vive-museum`을 더하고, `v*` 태그 push로 배포한다. 아래 "자동으로 다시 빌드"는 같은 워크플로를 다른 계기로 부르는 것이다.

### 전시 목록 관리: 정보는 프로젝트에, 다시 빌드는 자동 (2026-10-15 사용자 결정, 에이전트 제안의 C안)

- **전시 정보는 각 프로젝트 저장소에 둔다.** `deploy/exhibit.json`에 제목, 한 줄 설명, 썸네일 경로를 적는다. (형식은 제안. 영어·한국어를 함께 둘지는 미정)
- **주소는 따로 적지 않는다.** 배포에 이미 쓰는 `deploy/site.json`의 `subdomain`으로 `https://<subdomain>.yeonhyuk.me`를 만든다. 도메인을 바꾸면 박물관도 따라간다.
- **목록은 서브모듈 목록에서 온다.** 박물관 빌드가 루트 저장소의 `.gitmodules`에 있는 저장소를 돌며, 각 저장소 main의 `deploy/exhibit.json`을 GitHub에서 읽는다. 서브모듈 갱신 주기와 상관없이 늘 최신 정보를 쓴다. 전시 파일이 없는 저장소(예: 비공개 도구인 vive-infra)는 전시하지 않는다.
- **자동으로 다시 빌드한다.** 프로젝트의 deploy 워크플로가 끝날 때 박물관 저장소에 `repository_dispatch`를 보내, 박물관을 다시 빌드·배포한다. 박물관 저장소에 push할 때와 `ideas/`가 바뀔 때도 다시 빌드한다.
- **썸네일**: 저장소에 이미지를 넣어 두면 그것을 쓴다. 없으면 프로젝트 배포 뒤에 워크플로가 headless 브라우저로 사이트를 찍어 쓴다. 3D(WebGL) 화면은 자동 촬영이 잘 안 나올 수 있어서 직접 넣는 길을 남긴다.

### "준비 중" 전시 (2026-10-15 사용자 결정)

- 아직 구현하지 않은 아이디어도 전시한다. 목록은 루트 저장소의 `ideas/`에서 온다: 상태가 "아이디어", "보류", "구현 중"인 것은 "준비 중"으로, "폐기"는 전시하지 않는다.
- "준비 중" 전시품은 누를 사이트가 없다. 썸네일 대신 자리표시 그림을 둔다. (에이전트 제안)
- 같은 프로젝트가 `ideas/`와 서브모듈 양쪽에 있으면, 배포된 전시 정보가 있을 때 그것을 쓰고 아니면 "준비 중"으로 둔다. 아이디어 파일의 "저장소" 항목으로 둘을 잇는다. (에이전트 제안)

### 방문자 아이디어 (2026-10-15 사용자 결정, 에이전트 제안을 따름)

- 사이트의 입력 칸에서 아이디어를 받는다. 정적 사이트만으로는 받을 수 없어서, 작은 서버리스 함수(API Gateway + Lambda, vive-infra에 모듈 추가)가 받는다.
- 받은 아이디어는 **박물관 저장소에 GitHub Issue로** 만든다. 라벨(예: `visitor-idea`)을 붙인다. 이슈는 공개되어도 된다.
- **사용자에게 이메일로도 알린다.** (방법은 미정 사항 참고)
- 쓸 만한 이슈는 사용자가 고르고, 에이전트가 루트 저장소의 `ideas/`로 옮긴다. 이슈를 그대로 아이디어로 등록하지는 않는다. (에이전트 제안)
- 스팸 방지: Cloudflare Turnstile과 요청 수 제한을 함께 둔다.
- 이슈가 공개이므로 방문자의 이메일 같은 개인정보는 이슈에 적지 않는다. 연락처를 받는다면 따로 보관하거나 받지 않는다. (에이전트 제안)

## 미정 사항

- **박물관 저장소의 위치**: 지금 문서(AGENT.md)에는 박물관을 루트 저장소에 만든다고 되어 있다. 이슈를 "박물관 쪽 저장소"에 만들기로 했으므로, 두 가지 중 하나를 고른다.
  - 루트 저장소에 둔다: 이슈도 루트 저장소에 쌓인다. 저장소가 하나라 단순하다.
  - 박물관 전용 저장소(`vive-museum`)를 따로 만들고 서브모듈로 연결한다: 이슈가 박물관 쪽에만 쌓이고, 다른 프로젝트와 같은 구조가 된다. 이 경우 루트 저장소는 아이디어 문서와 서브모듈만 갖게 되고, AGENT.md의 역할 설명도 바꾼다.
- **이메일 알림 방법**
  - GitHub 알림: 이슈가 생기면 저장소를 Watch 중인 사용자에게 GitHub가 메일을 보낸다. 따로 만들 것이 없다. (에이전트 추천)
  - 직접 발송: Lambda가 Amazon SES로 메일을 보낸다. 제목·형식을 마음대로 할 수 있지만 SES 설정(도메인 인증)이 더 필요하다.
- 방문자 아이디어 입력 항목: 제목과 설명만 받을지, 종류(게임, 도구 등)나 닉네임도 받을지
- 방문자 아이디어를 사이트에 다시 보여줄지 (예: 최근 받은 아이디어 목록, 이슈 링크)
- 전시품에 더 보일 정보: 저장소 링크, 마지막 배포 버전과 날짜, 기술 스택, 만든 기간
- 전시 순서: 만든 순서, 최근 배포 순서, 직접 정하는 순서
- 언어: 영어·한국어 둘 다 낼지 (창고 타이쿤은 둘 다 지원한다)
- 기술 스택과 사이트 생성 도구 (디자인을 정한 뒤 고른다)
- 디자인 방향 ("박물관 느낌"의 구체적인 모습). Figma 후보를 받은 뒤 정한다.

## 메모

- 제안: 링크를 공유했을 때 보이는 미리보기 이미지와 설명(Open Graph)을 넣는다. 전시품마다 썸네일이 있으니 그대로 쓸 수 있다.
- 제안: 사이트가 휴대폰에서도 보이게 만든다. 다만 전시한 프로젝트가 PC 전용(창고 타이쿤)이면 전시품에 "PC 권장"을 표시한다.
- 제안: 방문 통계가 필요하면 CloudFront 로그나 가벼운 통계 서비스를 쓴다. 지금은 넣지 않는다.
- 제안: 방문자 아이디어에 공감(👍) 수를 받는 기능은 GitHub Issue의 반응으로 대신할 수 있다. 사이트에서 따로 투표를 받지는 않는다.
