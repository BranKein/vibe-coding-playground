# 프로젝트 박물관 사이트

- 상태: 구현 중
- 작성일: 2026-10-12
- 주소: https://vive-museum.yeonhyuk.me (호스팅은 2026-10-16에 만들었고, 첫 배포 v0.0.1은 Secrets 입력 뒤)
- 저장소: https://github.com/BranKein/vive-museum (`projects/museum`)

## 개요

정적 사이트 하나에 바이브 코딩 프로젝트들을 박물관처럼 전시한다. 전시품마다 썸네일이 있고, 누르면 그 프로젝트 사이트로 들어간다. 아직 만들지 않은 아이디어는 "준비 중"으로 전시한다. 방문자는 새 아이디어를 남길 수 있다.

## 요구사항

사용자가 말한 내용:

- 정적 사이트일 것
- 다른 프로젝트들을 보여줄 것
- 박물관 같은 느낌일 것
- (2026-10-15) 기능은 간단하게: 프로젝트마다 썸네일이 있고, 누르면 그 프로젝트 사이트로 들어간다.
- (2026-10-15) 다른 프로젝트의 도메인 링크를 알고 있어야 하고, 바뀌면 갱신되어야 한다.
- (2026-10-15) 방문자에게 아이디어를 받는다.
- (2026-10-15) 디자인이 중요하다. 에이전트가 틀에 박히지 않은 디자인 후보 10가지를 웹 시안으로 만들고, 사용자가 고른 뒤에 구현한다. (Figma를 쓰려던 계획은 뺐다)

## 결정된 사항

### 디자인: 네 가지 전시관을 모두 둔다 (2026-10-15 사용자 결정)

- 웹 시안 중 전시 도록, 폐관 후(야간 개장), 핀보드, 3D 전시관(안내판형, 12-B)을 남기고, 넷 다 유지한다. 방문자가 고른다.
- 머리말과 꼬리말은 네 전시관이 같은 것을 쓴다. 머리말에서 전시관 바꾸기, 언어(한국어·영어), 밝게/어둡게를 전환한다.
- 전시관 바꾸기는 머리말 버튼으로 여는 창에서 고른다. 고른 전시관, 언어, 밝게/어둡게는 브라우저에 기억하고, 첫 화면은 지난번 전시관으로, 처음이면 핀보드로 연다. (첫 전시관은 에이전트 제안)
- 네 전시관 모두 밝게/어둡게 색을 따로 정했다. 처음에는 방문자 기기의 설정을 따른다.
- 3D 전시관은 액자를 정면에서 보고, 화면 크기에 맞춰 액자와 안내판이 꽉 차게 다가간다. 휴대폰에서는 둘 다 작게 보이는 것이 남은 과제다.
- 폴더 이름은 `projects/museum` (사용자 결정).

### 저장소 (2026-10-15 사용자 결정)

- 박물관은 별도 저장소 `vive-museum`에 만든다. 다른 프로젝트처럼 루트 저장소의 서브모듈이다. 박물관도 바이브 프로젝트이므로 자기 자신을 다른 프로젝트와 똑같이 전시한다(2026-10-16 사용자 결정, 처음에는 전시하지 않기로 했었다). 썸네일은 전시 도록 화면을 찍은 것이다.
- 사이트 코드, 방문자 아이디어 함수(Lambda) 코드, 방문자 아이디어 이슈가 모두 이 저장소에 있다. 함수가 쓰는 AWS 자원(API, DB, 메일)은 다른 인프라처럼 vive-infra가 만든다.

### 주소와 배포 (2026-10-15 사용자 결정)

- 주소는 `vive-museum.yeonhyuk.me`.
- 배포는 다른 프로젝트와 같은 구조를 쓴다([docs/deploy.md](../docs/deploy.md)). vive-infra에 `sites/vive-museum`을 더하고, `v*` 태그 push로 배포한다. 아래 "자동으로 다시 빌드"는 같은 워크플로를 다른 계기로 부르는 것이다.

### 전시 목록 관리: 정보는 프로젝트에, 다시 빌드는 자동 (2026-10-15 사용자 결정, 에이전트 제안의 C안)

- **전시 정보는 각 프로젝트 저장소에 둔다.** `deploy/exhibit.json`에 제목, 한 줄 설명(영어·한국어), 기술 스택, 썸네일 경로, PC 권장 여부를 적는다. (형식은 에이전트 제안)
- **주소는 따로 적지 않는다.** 배포에 이미 쓰는 `deploy/site.json`의 `subdomain`으로 `https://<subdomain>.yeonhyuk.me`를 만든다. 도메인을 바꾸면 박물관도 따라간다.
- **목록은 서브모듈 목록에서 온다.** 박물관 빌드가 루트 저장소의 `.gitmodules`에 있는 저장소를 돌며, 각 저장소 main의 `deploy/exhibit.json`을 GitHub에서 읽는다. 서브모듈 갱신 주기와 상관없이 늘 최신 정보를 쓴다. 전시 파일이 없는 저장소(예: 비공개 도구인 vive-infra)는 전시하지 않는다.
- **자동으로 다시 빌드한다.** 프로젝트의 deploy 워크플로가 끝날 때 박물관 저장소에 `repository_dispatch`를 보내, 박물관을 다시 빌드·배포한다. 박물관 저장소에 push할 때와 `ideas/`가 바뀔 때도 다시 빌드한다.
- **썸네일**: 저장소에 이미지를 넣어 두면 그것을 쓴다. 없으면 프로젝트 배포 뒤에 워크플로가 headless 브라우저로 사이트를 찍어 쓴다. 3D(WebGL) 화면은 자동 촬영이 잘 안 나올 수 있어서 직접 넣는 길을 남긴다.

### 전시품에 보이는 것과 순서 (2026-10-15 사용자 결정)

- 썸네일, 제목, 한 줄 설명, 사이트 링크, 저장소 링크, 마지막 배포 버전과 날짜, 기술 스택, 만드는 데 걸린 날수.
- 버전과 날짜는 저장소의 가장 최근 `v*` 태그와 그 날짜에서 가져온다. (에이전트 제안)
- 걸린 날수는 첫 커밋부터 첫 배포(`v1.0.0` 태그)까지의 날수로 센다. 같은 날이면 1일. (에이전트 제안. 사용자가 "며칠 만에 다 만들었는지"라고 함)
- PC 전용 프로젝트에는 "PC 권장"을 표시한다.
- 순서: 마지막 배포 날짜가 최근인 것부터. "준비 중"은 그 뒤에, 아이디어를 적은 날짜가 최근인 것부터. (뒤쪽 순서는 에이전트 제안)

### 방문 통계 (2026-10-15 사용자 결정)

- Cloudflare Web Analytics를 붙인다. 무료이고 쿠키를 쓰지 않아 동의 배너가 필요 없다. 다른 프로젝트 사이트에도 같은 방식으로 붙일 수 있다.
- 어떤 전시품을 눌러 나갔는지는 기록되지 않는다. 궁금하면 각 프로젝트 사이트의 통계에서 박물관에서 들어온 방문을 본다.

### 언어와 화면 (2026-10-15 사용자 결정)

- 영어와 한국어 둘 다. 방문자의 브라우저 언어로 시작하고 바꿀 수 있다. (시작 언어는 에이전트 제안)
- 휴대폰에서도 보인다.
- 링크를 공유하면 미리보기(Open Graph)가 뜬다. 사이트 전체의 미리보기와, 가능하면 전시품마다의 미리보기.

### "준비 중" 전시 (2026-10-15 사용자 결정)

- 아직 구현하지 않은 아이디어도 전시한다. 목록은 루트 저장소의 `ideas/`에서 온다: 상태가 "아이디어", "보류", "구현 중"인 것은 "준비 중"으로, "폐기"는 전시하지 않는다.
- "준비 중" 전시품은 누를 사이트가 없다. 썸네일 대신 자리표시 그림을 둔다. (에이전트 제안)
- `ideas/` 문서는 한국어로만 쓰여 있다. 영어 화면의 "준비 중" 제목·설명은 아이디어 파일에 영어 한 줄을 함께 적어 둔다. (에이전트 제안)
- 같은 프로젝트가 `ideas/`와 서브모듈 양쪽에 있으면, 배포된 전시 정보가 있을 때 그것을 쓰고 아니면 "준비 중"으로 둔다. 아이디어 파일의 "저장소" 항목으로 둘을 잇는다. (에이전트 제안)

### 방문자 아이디어 (2026-10-15 사용자 결정)

받기:

- 입력 항목은 **제목, 설명, 이메일(선택)**. 이메일은 나중에 구현됐는지 알려 주기 위한 것이다. 비워 두면 알림 없이 아이디어만 남는다.
- 사이트의 입력 칸 → 서버리스 함수(API Gateway + Lambda). 함수 코드는 vive-museum 저장소에, AWS 자원은 vive-infra에 둔다.
- 스팸 방지: Cloudflare Turnstile과 요청 수 제한.

함수가 하는 일 (2026-10-15 사용자 결정: 사용자가 승인한 뒤에 이슈를 만든다):

1. 받은 아이디어(제목, 설명, 이메일)를 DynamoDB에 "승인 대기"로 저장한다. 아직 어디에도 공개하지 않는다.
2. 이메일을 적었으면 **확인 메일**을 보낸다. 방문자가 확인해야 알림 대상이 된다. 남의 주소를 적어 그 사람에게 메일이 가는 것을 막는다. 24시간 안에 확인하지 않으면 이메일만 지운다. (시간은 에이전트 제안)
3. **사용자에게 Amazon SES로 메일을 보낸다.** 제목, 설명, 방문자 이메일(적었으면), "승인"과 "거절" 링크가 들어간다. 방문자 이메일은 이 메일에만 들어간다.
4. 사용자가 **승인**하면 vive-museum 저장소에 GitHub Issue를 만든다. 라벨 `visitor-idea`. 이슈에는 제목과 설명만 적고, 이메일은 적지 않는다. 이슈는 공개되어도 된다.
5. 사용자가 **거절**하면 아이디어와 이메일을 지운다. 방문자에게는 알리지 않는다. 30일 동안 아무것도 누르지 않아도 지운다. (에이전트 제안)

메일 주소 (2026-10-15 사용자 결정):

- 사용자가 받는 주소: `yeonhyuk.public@gmail.com`
- 보내는 주소: `noreply@yeonhyuk.me` (에이전트 제안. SES로 보내려면 보내는 주소가 인증한 도메인이어야 해서, Gmail 주소로는 보내지 않는다)

링크 안전 (에이전트 제안):

- 승인·거절·이메일 확인·수신 거부 링크는 한 번만 쓰는 서명된 토큰을 담는다.
- 메일 보안 검사기가 링크를 미리 열어 보는 경우가 있어서, 링크를 여는 것만으로는 아무 일도 일어나지 않게 한다. 링크는 확인 화면을 열고, 화면의 버튼을 눌러야 처리한다.

보이기:

- 받은 아이디어는 사이트에 바로 보이지 않는다.
- 사용자가 정식 아이디어로 채택해 루트 저장소의 `ideas/`에 md 파일이 생기면, 그때 "준비 중"으로 전시된다. 아이디어 파일에 출처 이슈를 적어 둔다(예: `- 출처: vive-museum#12`). 이것이 이슈와 아이디어를 잇는 고리다. (에이전트 제안)
- 이슈를 그대로 아이디어로 만들지 않는다. 사용자가 고르면 에이전트가 `ideas/`로 옮긴다.

방문자에게 다시 알리기:

- 확인을 마친 이메일만 대상이다.
- 그 아이디어가 다 만들어져 전시되면(첫 배포), 방문자에게 "만들어졌다"는 메일을 SES로 보낸다. 박물관 빌드가 출처 이슈가 있는 아이디어의 상태가 "완료"로 바뀐 것을 보고, 알림 함수를 부른다. 알림 함수는 DynamoDB에서 이메일을 찾아 보내고, 보냈다고 표시해 두 번 보내지 않는다. (구조는 에이전트 제안)
- 채택됐을 때("준비 중"이 될 때)는 알리지 않는다. (2026-10-15 사용자 결정)
- 같은 방문자가 아이디어를 여러 개 남겼어도 메일은 아이디어마다 따로 보낸다. (2026-10-15 사용자 결정)
- 마지막 알림을 보낸 뒤에는 이메일을 지운다. 모든 메일에 수신 거부 링크를 넣는다. (에이전트 제안)

이 모든 것을 박물관 쪽 Lambda에서 처리할 수 있다. 받는 함수와 알리는 함수 두 개(또는 한 함수의 두 경로)면 된다.

- 디자인 방향: 정했다(위 "네 가지 전시관"). 시안 기록: 웹 시안(https://claude.ai/artifact/5qoAuSxUP8JXqn3daUQ2BG). 1차 10가지 중 설계 도면, 표본 서랍, 기념품 엽서는 뺐다(사용자 의견). 2차(2026-10-15)는 흰 벽, 입장권, 오디오 가이드, 전시 도록, 안내 표지, 카드 목록함, 폐관 후를 의견대로 고친 것과 새로 만든 핀보드(엇갈린 썸네일, 마우스를 올리면 펼침·뒤집힘), 3D 전시관(복도를 걷고 아래 썸네일 띠로 이동).

사용자가 해야 할 일 (구현 때 모아서 알린다):

- `vive-museum` 저장소 만들기
- SES: `yeonhyuk.me` 도메인 인증(DNS 레코드는 vive-infra가 Cloudflare에 만들 수 있다), `yeonhyuk.public@gmail.com` 주소 확인, **샌드박스 해제 신청**(이것을 해야 방문자에게 메일을 보낼 수 있다)
- Cloudflare Turnstile 사이트 키 발급
- 이슈를 만드는 GitHub 토큰(vive-museum의 Issues 쓰기 권한) 발급. AWS에 비밀 값으로 넣는다
- 다른 프로젝트들의 deploy 워크플로가 vive-museum에 신호를 보낼 수 있게 토큰 범위 넓히기

## 메모

- 제안: 이메일을 받으므로 입력 칸 아래에 짧은 개인정보 안내를 둔다(받는 항목: 이메일, 목적: 구현 알림, 보관: 알림을 보낼 때까지 또는 수신 거부 때까지). 안내 링크를 누르면 전문을 보여 준다.
- 제안: 제목·설명 길이 제한(예: 제목 100자, 설명 2,000자)과 요청 수 제한(예: 같은 IP에서 1시간에 5건)을 둔다. 수치는 구현 때 정한다.
- 비교 기록 (방문 통계): GA는 클릭 이벤트까지 볼 수 있지만 쿠키 때문에 동의 배너가 필요하고 무겁다. CloudFront 로그는 스크립트가 필요 없지만 직접 집계해야 하고 봇이 섞인다. CloudFront 콘솔의 기본 보고서는 설정 없이 볼 수 있다.
- 제안: 방문자 아이디어에 공감(👍) 수를 받는 기능은 GitHub Issue의 반응으로 대신할 수 있다. 사이트에서 따로 투표를 받지는 않는다.
